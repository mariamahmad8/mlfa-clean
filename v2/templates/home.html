How the hub works

The MLFA Email Hub watches your info@ inbox, uses GPT to sort each incoming email into a category, then either handles it automatically or hands it to a person to review.

Everything is configurable. You control which categories exist, what happens when an email matches each one, who gets forwarded what, and what auto-reply gets sent. The hub is designed so that a non-technical staff member can adjust behavior without touching code.

The three pieces

  1. The worker — a background program that polls Microsoft every ~30 seconds for new emails. You never see it.
  2. The Hub — this website. Staff review emails, edit settings, view audit history.
  3. The classifier — GPT reads each new email and decides which category it belongs to.

The life of an email

Every incoming email follows this path:

  1. Arrives at info@mlfa.org in Outlook.
  2. Worker picks it up within ~30 seconds on the next poll.
  3. Classifier reads it — GPT decides which category (donor, legal, jail_mail, volunteer, etc.).
  4. Router builds a plan — based on the category's rules: which folder to move to, who to forward to, what auto-reply to send, what tag to apply.
  5. Automation mode splits the path:
    • Automation on → plan executes immediately. Email gets forwarded, replied to, tagged, and moved.
    • Automation off → email lands in the review queue in the Hub. A staff member approves, rejects, or dismisses it.
  6. Outlook tag applied — PAIRActioned/<category> so the worker doesn't re-process it.
  7. Audit log entry written — records what happened, who did it, when.
ImportantOnce tagged with PAIRActioned, the email is never touched again by the worker. That's how we avoid double-processing.

The Automation toggle

The switch at the top of the Hub. Two states:

  • Off — every email waits in the queue for a person. Safer, slower.
  • On — the AI processes emails immediately without human review. Fast, but you trust the classifier fully.
Important — automation always skips unknownsEven with automation ON, an email GPT can't confidently classify (empty categories, or a category with no matching rule) still gets sent to the review queue as a safety guardrail. Automation makes the known cases faster; it doesn't blindly auto-process everything.

Admins and owners can toggle this. Reviewers cannot.

How the worker polls Microsoft

The worker is a background process that runs on a timer, asks Microsoft for new emails, and hands them to the pipeline.

The poll cycle

  1. Worker wakes up every ~30 seconds (configurable via POLL_INTERVAL_SECONDS).
  2. For each active inbox in the database, it asks Microsoft Graph: "any changes since the last time I asked?"
  3. Microsoft returns a batch of changed messages plus a new delta token.
  4. Worker saves the new delta token to the inbox row (columns delta_token_inbox and delta_token_junk).
  5. For each returned message, it checks: is it already tagged PAIRActioned? If yes, skip. Otherwise send it to the pipeline.

Delta token vs backfill

  • Delta token = a bookmark Microsoft gives us that means "you've seen everything up to this point." Next call, we hand it back and only get new stuff since then.
  • Backfill = the very first poll for an inbox, before any delta token exists. Uses the Backfill days setting to fetch every unread email received in the last N days. After the first backfill completes, subsequent polls use delta sync.

What happens when the delta token breaks

Microsoft occasionally invalidates delta tokens (rare, but happens on mailbox reconfiguration, folder moves, or after extended periods). When the worker hits SyncState or 410 errors:

  1. The current delta token is thrown away.
  2. Next poll falls back to backfill mode using the inbox's Backfill days setting.
  3. A new delta token is established after backfill completes.
  4. The event is logged as o365.delta_token_invalid in security logs.

What the worker fetches per message

To minimize bandwidth and latency, the delta query only selects: id, conversationId, isRead, receivedDateTime, from, sender, subject, categories. The full body is fetched with a separate msg.refresh() call only if the message passes the "not tagged" filter.

IdempotencyThe PAIRActioned tag check is the single mechanism preventing double-processing. If you manually clear a message's Outlook categories, the worker will re-process it on the next poll as if it were fresh.

How the classifier works

The classifier assembles a prompt for GPT and interprets its response into a ClassificationResult.

The prompt structure

Every classification request sends GPT a system prompt built from:

  1. Inbox system_preamble — the intro text from Settings → Inboxes → Edit → AI behavior. Explains what MLFA is and what this inbox does.
  2. All active category rules — each category's key + label + rule text.
  3. Inbox global_guidelines — the closing rules, including the required JSON output schema.

Then a user prompt containing:

  • The current email's from, subject, and body.
  • If Use conversation history is on: earlier messages in the same thread.
  • Existing PAIRActioned tags on this message (rare, only relevant for reprocessing edge cases).

What GPT returns

GPT is instructed to reply as JSON with:

  • categories — list of matched category keys.
  • all_recipients — email addresses the AI thinks should be involved.
  • needs_personal_reply — boolean. When true, the router picks the personal reply template if the category has one.
  • escalation_reason — string explaining why personal reply is needed.
  • name_sender — the sender's name for the greeting substitution.
  • amount_detected — extracted dollar figure or null.
  • reason — dict mapping each category to a plain-English justification. Shown in the Hub's Reason field.

Category filtering

After GPT responds, the classifier filters the returned categories against the list of active rules for that inbox. Any category GPT invented that doesn't exist in your rules gets dropped. If the filtered list ends up empty, that's the "unknown category" case handled by the router.

When classification fails

If GPT returns invalid JSON, times out, or errors — the classifier returns an empty ClassificationResult (no categories, no recipients). Router treats this the same as "unknown" → forces human review.

Where the classifier's blind spots areThe classifier does NOT see: Outlook categories set by humans, the email's attachments, prior classifications of the same conversation (only thread messages themselves), or the email's headers beyond from/subject.

How the router decides

Given a classification, the router builds a MessageActionPlan: which folder to move to, who to forward to, what auto-reply to send, and whether the email needs human review.

Step by step

  1. Find matching rules. Loop over active category rules; keep any whose key is in the classification's categories list.
  2. Empty match check. If no rules match, force human review regardless of automation setting.
  3. Sort by priority. Lowest priority number = highest importance (1 wins).
  4. Skip check. If the top rule has skip=true (legacy field, hidden from UI), do nothing at all.
  5. Folder decision. Take the top rule's folder_path. Special value Deleted Items or the delete_immediately flag means "delete instead of move."
  6. Forwarding. Gather every recipient email from every matching rule (union). Apply amount thresholds — a rule with a threshold contributes zero recipients if amount_detected is below it.
  7. Auto-reply. Walk matching rules in priority order. First one with auto_reply_enabled=true and a template picks the reply. Reply safeguard check happens here.
  8. Mark-read decision. Conservative: if ANY matching rule has mark_read=false, leave the email unread.
  9. Tag. Comma-joined keys of all matching rules. Used by the adapter to write PAIRActioned/<key> tags.
  10. Human review. requires_human_review = not inbox.automation_mode. Unless the empty-match check already forced it to true.

Multiple categories, all fire independently

If GPT returns [donor, grant] and both rules match, the email will be:

  • Tagged as BOTH PAIRActioned/donor AND PAIRActioned/grant.
  • Forwarded to the UNION of both categories' recipients.
  • Moved to the folder of whichever rule has the higher priority (lower number).
  • Get the auto-reply from the highest-priority rule that has a template.

Internal domain handling

The hub distinguishes "external senders" (donors, applicants, public) from "internal senders" (@mlfa.org staff). Internal senders get different treatment in multiple places.

Where "internal" is determined

On Settings → Inboxes → Edit → Filters, the Internal email domains field lists domains treated as staff. Typically mlfa.org. Any email whose sender address ends with @mlfa.org (or matches the domain exactly) is considered internal.

What "sent by info@mlfa.org" means

info@mlfa.org is the watched mailbox itself. Emails sent from that address are outbound — they never come back through the poller, so the worker never sees them at all. Rachel's replies from rachel.smith@mlfa.org (on behalf of info@) sit in the Sent Items folder, not the Inbox. The worker doesn't poll Sent Items.

The three places internal-sender checks fire

  1. Skip-if-internal on categories. If a category has skip_if_internal=true and the current email's sender is internal, that category won't be applied to that email. Prevents auto-replying to staff who forwarded an email using their own account.
  2. Internal reply bridge. When enabled, incoming emails from internal senders whose body starts with [EXTERNAL] or [INTERNAL] get special handling. See Internal reply bridge.
  3. Outbound action suppression. Some code paths suppress auto-reply/forward for internal senders even if the category didn't explicitly opt in.

Concrete scenario

Rachel forwards a legal email from her personal @mlfa.org account into info@mlfa.org. What happens:

  1. Worker polls, sees the forward, sender = rachel.smith@mlfa.org.
  2. Classifier runs, likely returns legal.
  3. Router checks matching rules. If legal has skip_if_internal checked, the router drops that rule from the match set.
  4. If NO other rules match, router forces human review (the empty-match guardrail).
  5. If some other rule matches (say active_communication without skip_if_internal), the email flows through that instead.

Individual emails within a thread still get tagged

Each incoming message is processed independently. If a thread has 5 messages that all arrive at info@mlfa.org over time — from Rachel, then a donor, then Rachel again, then another external person — each one gets its own classification and tagging based on its own sender. Rachel's are internal (may be skipped), the donor's are external (processed normally).

Why sometimes it looks like the whole thread was skippedIf the current message is from an internal sender and gets skipped, and the thread's earlier messages (also processed individually) happened to also be internal or match no active rule, the thread appears untouched. But each was evaluated on its own.

Thread context in detail

When Use conversation history is on for an inbox, the classifier gets extra context: earlier messages in the same conversation.

How it's fetched

When a new email arrives, the worker calls get_thread_messages() passing the email's conversationId. Microsoft returns every message in that conversation, excluding Deleted Items and the current message itself.

What gets included in the prompt

The classifier includes each thread message's sender, subject, and body in the user prompt. GPT sees them chronologically. This lets it recognize follow-ups ("Following up on this?") that would be ambiguous in isolation.

Thread tags

The worker also fetches thread_tags — every Outlook category currently on any message in the conversation. Used by the reply safeguard (see below) to detect "have we already replied to this thread as legal?" without needing to reclassify old messages.

Limits

  • Thread context is limited to the first N messages (~10) to keep the prompt from ballooning.
  • If the earlier thread messages went to a different mailbox that the worker doesn't watch, they won't be in Microsoft's conversation view for info@mlfa.org and thus won't be included.
  • If Use conversation history is off, none of this applies. Classifier only sees the current message.

Why it's off by default for Test & Preview

The Test & preview tool passes an empty thread. This means a fake email that would classify correctly with thread context might classify differently in the tool — that's expected. Real emails get real thread data.

Reply safeguard

Prevents sending the same auto-reply twice on the same conversation.

The check

Before sending an auto-reply for category X, the router looks at thread_tags for any tag matching PAIRActioned/<X>. If found, the safeguard fires and the reply is suppressed.

What still happens when the safeguard fires

  • Auto-reply is skipped for THIS message.
  • The rest of the plan still runs: forwarding, tagging, folder move, mark-read.
  • The email still ends up tagged PAIRActioned/<X>.

Concrete scenario

Applicant emails asking about their case. Legal category has an auto-reply "please submit an application at ..." with safeguard on.

  1. Email 1 — new inquiry. Router sees no prior PAIRActioned/legal in thread. Safeguard passes. Reply sent. Message tagged PAIRActioned/legal.
  2. Email 2 — applicant replies "thanks, but I have another question." Router sees Email 1 is already tagged PAIRActioned/legal. Safeguard fires. No second reply. Email 2 still tagged with PAIRActioned/legal.

Applicant gets exactly one auto-reply per thread, even if they email 5 times.

Amount threshold

A per-category rule that only forwards to recipients when GPT detected a dollar amount at or above the threshold.

How the amount is extracted

GPT is asked to return amount_detected as part of its JSON response. It reads the email body and returns the primary dollar figure (donation amount, invoice total, etc.), or null if it can't confidently identify one.

How the router applies the threshold

When gathering recipients for a category with amount_threshold set:

  • If amount_detected is null → skip this category's forwarding (defensive).
  • If amount_detected < threshold → skip this category's forwarding.
  • If amount_detected ≥ threshold → include this category's recipients in the forward list.

Only forwarding is affected — the email is still tagged, still gets the auto-reply, still gets moved to the folder. The threshold ONLY gates the forward.

Typical use

  • Donor category with threshold $1000 → small donations don't ping the giving team, large ones do.
  • Invoice category with threshold $1000 → routine invoices skip the finance team notification.
The AI can be wrong about amountsIf an email says "we already gave $50 last year and want to donate more this year," GPT might extract $50 or might extract nothing. Always spot-check amount detection when tuning thresholds.

Cascade behaviors

Editing a template or recipient automatically updates every category that uses it — you never have to re-select.

Template edit cascade

When you save an edit to a Reply Template, the storage layer:

  1. Reads the template's current body from the database (pre-update).
  2. Updates the template row with the new body.
  3. Finds every category rule whose stored reply_template body matches the pre-update body, and rewrites them with the new body. Same for reply_template_personal.

Effect: your category rule instantly reflects the new template text without needing to re-select the template in the category editor.

Recipient email cascade

When you change a recipient's email address in Settings → Recipients, the storage layer:

  1. Reads the recipient's current email.
  2. Updates the recipient row.
  3. Runs a JSONB UPDATE on every category rule's emails_to_forward array in the same inbox, swapping the old address for the new one.

Recipient delete cleanup

Deleting a recipient strips their address from every category's forwarding list on the same inbox. No stale addresses linger.

Inbox delete cleanup

Deleting an inbox strips its ID from every user's assigned_inbox_ids array before the actual DELETE runs. Prevents users holding stale references to inboxes that no longer exist.

Priority & ordering

Category priority controls what happens when multiple rules match one email.

Where priority is set

Each category rule has a priority integer. Lower numbers = higher priority. You reorder by drag-and-drop in Settings → Categories. Drag handles are the ⋮⋮ icons on the left of each row.

When new categories are created

A newly-created category is assigned priority max(existing) + 1 — one more than the current highest number, meaning it lands at the bottom of the list. You can drag it up if it should be checked before some existing categories.

What priority affects

  • Folder move — the highest-priority matching rule's folder wins.
  • Auto-reply — the first matching rule (by priority) that has a template + auto_reply_enabled sends the reply.
  • Forwarding — priority does NOT affect this. Every matching rule contributes its recipients to a union.
  • Tagging — every matching rule's key is applied.
  • Mark-read — conservative: if any matching rule says don't mark read, don't.

Classification is NOT priority-based

Priority is only used by the router after GPT has already classified. GPT doesn't know about priorities — it returns whatever categories fit best. If you want to influence what GPT picks, edit the classification rule text, not the priority.

The pending queue

Database table that stores emails waiting for human review.

What gets stored per queue entry

  • message_id — the Microsoft Graph message ID (used to fetch the real email if needed).
  • inbox_id — which inbox the message belongs to.
  • sender, subject_email, body_email — snapshot of the email at classification time.
  • classification — JSONB with the categories, recipients, reason, amount_detected, needs_personal_reply, escalation_reason, name_sender.
  • received_at, created_at — timestamps.

How it's populated

The pipeline calls queue.add_to_queue() when:

  • The inbox has automation off, AND classifier returned matching rules → queue with the plan attached.
  • The classifier returned no matching rules (unknown category) — regardless of automation state.
  • The inbox has send_to_openai=false — every email queues without classification.

How entries are cleared

  • Approve — the plan runs (reply, forward, tag, move), then the queue row is deleted.
  • Reject — the email is moved to Trash and the queue row is deleted.
  • Dismiss — the email is marked read and the queue row is deleted.
  • TTL cleanup (planned) — a scheduled job clears entries older than the inbox's Retention days setting.

What if the reviewer approves but the message has been deleted from Outlook?

The Approve action tries to execute the plan against the Microsoft message. If the message no longer exists, the plan fails (log entries appear as pipeline.reply_failed, pipeline.forward_failed). The queue row is still deleted so it doesn't sit forever.

What the audit log stores

Append-only table. Every action writes a row. Rows are never deleted or edited.

Columns

  • created_at — timestamp in UTC.
  • inbox_id — which inbox the action belongs to (nullable for global actions like user_created).
  • email / email_id — the target of the action. For email actions, it's the Microsoft message ID. For settings actions, it's a slug like rule:donor.
  • action_taken — one of a fixed set: auto_processed, queued_for_review, approved, rejected, dismissed, rule_created, rule_updated, rule_deleted, recipient_*, template_*, inbox_*, user_*, inbox_cloned.
  • actor — email address of the user who did it, or the string system for worker actions.
  • comment — free-text. For email actions, usually the classification comma-list. For settings actions, a summary like "Label: Donor Inquiry".
  • duration_ms — how long the pipeline took (for email actions).

What the audit log does NOT store

  • The email body. Only email_id — you'd have to look up the message in Outlook to see the content.
  • The specific fields that changed on an Update. Only that an update happened.
  • The full classification JSON. Only the categories as a comma string.

Tag mechanics in depth

Every action of consequence writes an Outlook category tag. The tag is the source of truth for "has this been handled?"

The three tag forms

TagWhen writtenWhen removed
PAIRActionedAlways, whenever the pipeline touches a message.Never automatically. Only if a human clears it manually in Outlook.
PAIRActioned/<key>When a category matches. One tag per matching category (multiple possible).Never automatically.
PAIRActioned/queuedWhen an email goes into the review queue.When Approve, Reject, or Dismiss is clicked (before the final action tags are written).

The poller's tag check

Every message returned by fetch_messages_delta and fetch_unread_since is checked with:

if any((t or "").startswith("PAIRActioned") for t in msg.categories):
    continue

If any category on the message starts with PAIRActioned, the worker treats it as already-handled and skips it entirely. No re-classification, no reprocessing.

What happens if you manually add PAIRActioned to a message in Outlook?

The worker skips it forever. This is a legit way to tell the hub "leave this specific email alone" — just apply the PAIRActioned category to it manually.

What happens if you manually remove PAIRActioned from a processed message?

The worker will reprocess it on the next delta sync. If automation is on and the classification result is stable, the actions will run again (potentially sending a duplicate auto-reply unless the reply safeguard catches it).

Automation mode rules

The full decision matrix for whether an email gets auto-processed or goes to the review queue.

AutomationSend to OpenAIMatching rulesOutcome
OFFONanyQueue for review, tag PAIRActioned/queued. Reviewer approves or rejects.
OFFOFF—Queue with special "AI disabled" flag, tag PAIRActioned/queued. Reviewer manually assigns category.
ONON1+ matchAuto-process. Plan executes, tags written, no queue entry.
ONON0 match (empty)Force-queued as safety guardrail. Same as OFF with matches.
ONOFF—Queue with "AI disabled" flag. Automation setting is ignored when AI is off — human review is always required for unclassified email.

Why the guardrail exists

Auto-processing an email with an unknown category would mean running an empty action plan — no forward, no reply, no folder move, just a tag. That's effectively "silently drop this email." Never desirable. The guardrail ensures human eyes see anything the AI couldn't confidently place.

Internal reply bridge

Optional feature that lets staff reply to a forwarded email using their own account, and have the hub relay their reply back to the original external sender.

Setup

  • Turn on Enable internal reply bridge in Settings → Inboxes → Edit → Advanced.
  • Set the internal and external prefixes (defaults: [INTERNAL] and [EXTERNAL]).

Forward-with-bridge mechanics

When a category matches and forwards to a staff person, and the bridge is enabled:

  1. Instead of a plain forward, the system uses forward_with_reply_bridge().
  2. The forwarded email includes visible instructions ("Start your message with [EXTERNAL]...") at the top.
  3. A hidden REPLY_ID_TAG is embedded in the body, tying the forwarded copy back to the original message ID.

How staff replies are detected

When any incoming email hits info@mlfa.org, the worker runs detect_internal_reply():

  1. Must have bridge enabled on this inbox.
  2. Sender must be internal (matches Internal domains).
  3. Body must contain the hidden REPLY_ID_TAG (means it came from a bridge-forwarded email).
  4. Must not already be PAIRActioned.
  5. Body content is scanned for the prefix.

The prefix behaviors

  • [EXTERNAL] — strip the prefix, send the reply back to the original external sender using info@mlfa.org as the from address.
  • [INTERNAL] — keep it internal, tag and file, don't relay.
  • No prefix — treat as normal internal email, no relay. The bridge only activates on the explicit prefix.

Why the bridge exists

Some MLFA workflows require staff to be able to answer forwarded questions personally (adding their own tone or case-specific details) while keeping the outbound thread on info@ so subsequent responses come back through the hub. Without the bridge, staff either have to blind-CC info@ every time or write from info@ directly, both of which are cumbersome.

Edge cases & FAQs

Why do some emails stay in the Inbox with no tag?

A few reasons:

  • Sent by someone at info@mlfa.org — the worker only processes incoming mail. Emails sent from the mailbox itself stay untouched.
  • Sender is on the "Ignore senders" list — the worker silently skips these. No tag, no processing.
  • The worker was down when the email arrived, and the delta token hasn't been rebuilt yet. Rare.
  • The email was already tagged manually in Outlook before the hub was set up — but doesn't start with PAIRActioned. The hub only skips messages that start with that prefix.

Why do some emails have PAIRActioned/<key> but stay in the Inbox?

Three possibilities:

  • The category has no destination folder — email was classified and tagged, but has nowhere to move.
  • The folder path has a typo or invalid syntax — the move failed silently. Test by moving the folder manually and check the path matches exactly (case-sensitive, forward slashes for nesting).
  • Someone in the thread replied from the same mailbox — Outlook's threading UI may show the original email "in the inbox" even though it was actually moved. Check the message's real folder location, not the conversation view.

Why does the AI classify a follow-up email differently than the original?

Because the AI sees the current message and (optionally) thread context — not always the full history. If the earlier messages in the thread went to a different address (not info@mlfa.org), the hub never saw them, so the classifier only has the current short follow-up to go on. This is expected behavior; tune the classification prompts to catch short follow-ups that reference the subject line.

Rachel replied to an email — does the hub know?

No. The hub only sees incoming messages. Rachel's outgoing reply from her @mlfa.org address doesn't come back through the worker. The "Reply Completed" badge you might see in Outlook is Outlook's own feature, not the hub.

Why did the same donor email get tagged both donor and grant?

Because GPT decided the email matched both category prompts. Categories aren't exclusive. If the donor prompt says "donations" and the grant prompt says "matching-gift programs, PayPal Giving Fund" and the email mentions both, both apply. Multiple tags means multiple actions can trigger (forward to give@ AND to grants team, for example).

What happens if GPT returns an unknown category?

Router forces the email into the review queue as a safety guardrail — even if automation is on. This prevents auto-processing something the system doesn't have a plan for.

Can I make the AI learn from my rejections?

Not yet. Rejection reasons are logged in the audit log but not currently fed back into the classifier. This is on the roadmap (RAG / memory of past corrections) but not built.

What if two staff members open the same queued email at the same time?

Whoever clicks Approve/Reject/Dismiss first wins. The other person will see it disappear from their queue on the next auto-refresh.

Do rejected emails come back?

Rejected emails are moved to Outlook's Deleted Items folder and tagged so the worker skips them on future polls. They won't be re-processed unless someone manually removes the tag and moves them back.

Does the worker poll the Junk / Spam folder?

Yes, if you've configured it to. Both the Inbox and JunkEmail folders have their own delta tokens (delta_token_inbox and delta_token_junk). Set up per inbox. Junk polling is optional — the majority of MLFA inboxes only poll Inbox.

Does the hub see attachments?

No. The classifier ignores attachments entirely — it only reads the sender, subject, and text body. Auto-replies and forwards preserve any attachments through Microsoft's forward/reply mechanism, but GPT never sees the file contents.

What language does the classifier work in?

GPT can classify emails in any language it understands — English, Arabic, Spanish, etc. The classification prompts you write are in English but describe the concepts; GPT applies them to whatever language the email is in.

Why did my auto-reply arrive with "Dear Sender," instead of the person's actual name?

Because GPT's name_sender came back null — the email didn't have a clearly identifiable name in the From header or signature. The {{greeting}} variable falls back to a generic time-of-day greeting like "Good afternoon,". Not a bug — it's the fallback.

What if the same email is sent twice by mistake?

Microsoft treats them as separate messages with different message IDs. The hub processes both independently. If the sender's second attempt has the same content, GPT will classify it the same way. The reply safeguard prevents duplicate auto-replies since both emails share a conversationId, but the forward and tag actions run for both.

How does the hub handle bounced / undeliverable notifications?

They're just emails with weird From addresses. The classifier reads them and tries to categorize. Typically these hit the auto_reply category (out-of-office and bounce messages) which sends them to Trash immediately.

What happens if two admins edit the same category at the same time?

Last-write-wins. Whichever admin saves last overwrites the other's changes. There's no locking, no conflict detection. In practice: coordinate before major category edits.

Is anything encrypted at rest?

Railway's managed Postgres provides at-rest encryption by default. However, the classification snapshots (reasoning + name_sender fields) sit in plaintext in the pending_queue column. Encryption of those specific fields is on the roadmap.

Does the hub retain email data after a queue entry is deleted?

The queue row is deleted immediately on Approve/Reject/Dismiss. But Postgres backups managed by Railway may retain a copy for the backup retention window. If you need to guarantee no lingering copies, MLFA should coordinate backup retention with Railway directly.

Can I see which categories a specific email hit before it was actioned?

Yes — the audit log's comment field on auto_processed or queued_for_review entries lists the categories comma-separated. Filter the audit log for that email's message_id in the Target column.

What happens when a session token expires mid-approval?

The frontend gets a 401 from the API call and redirects to /login. Any in-flight approve/reject action is not executed. Re-sign-in and try again — the email is still in the queue.

Why did an email get classified as "active_communication" when it looks like a donor question?

Two possibilities. Either the message body is very short (like a follow-up "any update?") and GPT weighted the body more than the subject; or your donor category prompt doesn't cover this specific variant. Fix by tightening the donor category prompt with example situations that include short follow-ups, or make active_communication's prompt more restrictive (only for truly ambiguous ongoing threads).

Does the hub understand when someone at MLFA answers an email that came through the hub?

Partially. If Rachel replies from her @mlfa.org account, her reply doesn't come back through info@mlfa.org, so the worker never sees it. But if the reply-all includes info@ or if the original external sender responds again to a thread that includes info@, the hub sees the follow-up and can apply the reply safeguard based on thread_tags.

Can I disable a specific category temporarily?

Yes — open the category and uncheck the "Active" toggle. GPT stops applying that label until you re-enable it. Existing tagged emails are unaffected.

What if I want an inbox to only queue everything for review, never auto-process?

Turn off the automation toggle on that inbox. Every incoming email will queue. Reviewers see them all in the Hub.

What if I want to disable AI classification entirely for one inbox?

Turn off send_to_openai in that inbox's settings. Emails will queue with an "AI disabled" flag and no categories, waiting for a human to route them manually.

Troubleshooting

An email should have matched a category but didn't

  1. Go to Settings → Test & preview.
  2. Paste the exact subject, sender, and body.
  3. Run the test and see what GPT returned.
  4. If it returned nothing — tighten the classification prompt on the target category with a positive example.
  5. If it returned the wrong category — tighten that category's prompt with a negative example ("Do NOT classify as X if...").

An auto-reply didn't send

  • Check the category has Send the auto-reply toggled on.
  • Check the category has a Reply template selected (not "Don't send an auto-reply").
  • Check the template's Active box is checked.
  • Check the Reply safeguard — if the thread already got a reply, subsequent messages in the same thread won't get another one.

A forward didn't go to the right person

  • Open the category, check the Forward list — the person's checkbox should be ticked.
  • If they were checked but no email went — check the recipient's Active flag in Settings → Recipients. Inactive recipients are excluded.
  • For donor/invoice: check the Amount threshold. If set, the forward only happens when GPT detected a dollar amount at or above that number.

Automation is on but emails still go to the queue

  • Check that automation is actually saved as on in Settings → Inboxes → Edit. The Hub toggle sometimes reflects state before a save completes.
  • If yes, the queued emails are the "unknown category" safety guardrail — GPT returned something the router doesn't recognize. Test them in Test & Preview to see what GPT is returning.

The Hub says "Session expired"

Sessions time out after 30 minutes of inactivity or 8 hours absolute. Sign in again.

I can't see one of my inboxes

You're either not assigned to it (ask an admin) or your role is Reviewer with restricted access. Admins see all inboxes automatically; owners and reviewers see only their assigned ones.

An email arrived but isn't showing up in the queue OR the Inbox tagged folder

  • Check the sender against the inbox's Blocked senders list.
  • Check if it's tagged PAIRActioned/queued but not appearing — could be a queue vs. inbox display mismatch.
  • Look at the audit log for that message_id — it may have been actioned and moved to a folder you didn't expect.

The classifier gave a category that shouldn't exist

GPT sometimes invents category names. The router filters unknown categories out — if GPT returned [legal, urgent] and there's no urgent rule, only legal is kept. If NO categories survive filtering, the email queues for human review. Fix by adjusting the classification prompts to only reference valid keys, or by adding the missing category.

An auto-reply sent to the wrong person

  • Check the reply template — is it hard-coding a name or address? Should only use {{greeting}} for personalization.
  • Check the reply is going TO the original sender, not to a recipient in the forward list. Auto-replies always go to the message's From, not to forwards.

A category is not appearing in the reply-template dropdown

The template must be marked Active to appear in dropdowns. Check Settings → Reply templates.

The pending queue is growing and nobody's acting on it

Common if MLFA staff is out or if too many emails are getting queued. Options:

  • Enable Automation on the inbox so classifications with matching rules run automatically.
  • Use the "Approve all pending" button in the Hub to bulk-approve after a quick scan.
  • Reduce false-queue rate by tightening categories — the router forces queue when no rules match, so if lots of emails have no match, add categories to cover them.

Delta sync appears stuck / no new emails coming through

  • Check Railway logs for o365.delta_token_invalid — the token may have been invalidated. The worker will fall back to backfill on the next poll.
  • Check if the worker process is actually running. On Railway, look at the service's status.
  • Check Microsoft Graph is healthy — very rare, but Microsoft has outages.

Two staff replied to the same email from different accounts

This is an Outlook/human coordination issue, not a hub issue. The hub sees each reply as it comes back through info@ (if it does) and treats them independently. Consider using the Automation toggle to fully automate replies for common categories so staff don't duplicate.

Rachel says a category isn't forwarding but it should be

  1. Open the category → confirm recipients are checked.
  2. Check recipients' Active flag in Settings → Recipients.
  3. Check the amount threshold — if set, GPT must have detected an amount at or above.
  4. Test the exact email in Test & preview and read the Forward to field in the result. If it's empty there, tighten the classification or fix the recipient linking.
